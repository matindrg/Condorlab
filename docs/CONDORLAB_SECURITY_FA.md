# سند جامع معماری امنیت و انطباق با استانداردها (Condorlab Security Architecture)

> **نسخه:** ۱٫۰ — تدوین استاندارد امنیتی OWASP ASVS سطح ۲ و خط‌مشی مقابله با تهدیدات  
> **تاریخ:** آبان ۱۴۰۵  
> **مبنا:** `CONDORLAB_PRD_FA-V3.md` (بخش ۳٫۲ NFR امنیت و پیوست هـ)، `SECURITY.md`  
> **استاندارد مرجع:** OWASP Application Security Verification Standard (ASVS 4.0.3) Level 2  
> **وضعیت:** سند مرجع امنیت نرم‌افزار، زیرساخت سرور و خط‌مشی کدنویسی امن.  

---

## ۰. اصول راهبردی امنیت کندرلب

1. **دفاع در عمق (Defense in Depth):** امنیت به یک لایه (مثلاً فایروال) متکی نیست؛ اعتبارسنجی در لایه Nginx، گیت‌وی شبکه، میدل‌ورهای NestJS، گارد‌های مجوز، و در سطح دیتابیس تکرار می‌شود.
2. **عدم افشای اطلاعات در خطاها (Zero Information Leakage):** خطاهای سیستمی، کدهای استک‌تریس یا خطاهای دیتابیس هرگز به کلاینت ارسال نمی‌شوند. پاسخ‌های خطا حاوی کد خطای یکتا و پیام عمومی امن هستند.
3. **اصل حداقل دسترسی (Least Privilege):** هر نقش کاربری (ادمین، مصحح، پشتیبان، دانش‌آموز) فقط و فقط به اندپوینت‌ها و جداولی دسترسی دارد که برای انجام وظیفه‌اش ضروری است.
4. **حفاظت تغییرناپذیر از مالک سیستم:** حساب `Grandmaster Admin` دارای لایه‌های حفاظتی سطح پایین در دیتابیس و کدهای سرور است و تحت هیچ سناریویی قابل تغییر یا حذف توسط سایر مدیران نیست.

## ۱. انطباق با چک‌لیست OWASP ASVS سطح ۲

```
┌─────────────────────────────────────────────────────────────────┐
│               حوزه‌های اعتبارسنجی OWASP ASVS                    │
├─────────────────┬─────────────────┬──────────────┬──────────────┤
│  احراز هویت     │  کنترل دسترسی   │ اعتبارسنجی   │ رمزنگاری     │
│  (V2 - Auth)    │  (V4 - Access)  │ ورودی (V5)   │ داده‌ها (V6) │
│  Argon2id/MFA   │  RBAC Guards    │ Zod Pipes    │ TLS 1.3/AES  │
└─────────────────┴─────────────────┴──────────────┴──────────────┘
```

### ۱٫۱. احراز هویت و مدیریت نشست (V2 & V3)
- **هشینگ گذرواژه‌ها:** استفاده اجباری از الگوریتم `Argon2id` (مقاوم در برابر حملات GPU و ASIC). استفاده از MD5، SHA-1، یا SHA-256 بدون Salt اکیداً ممنوع است.
- **کوکی‌های بدون دسترسی جاوااسکریپت:** توکن‌های دسترسی و نشست در کوکی‌های دارای فلگ‌های `HttpOnly`، `Secure` و `SameSite=Lax` صادر می‌شوند تا از سرقت توکن از طریق اسکریپت‌های مخرب (XSS) جلوگیری شود.
- **انقضای سشن:** رفرش‌توکن‌ها پس از ۳۰ روز منقضی شده و با هر بار استفاده در فرآیند رفرش، چرخش (Token Rotation) پیدا می‌کنند.
- **احراز هویت دومرحله‌ای (MFA):** برای نقش `Grandmaster Admin` و کارشناسان مالی اجباری است (استاندارد TOTP RFC 6238).

### ۱٫۲. کنترل دسترسی و مجوزها (V4)
- **بررسی مالکیت در سطح شیء (IDOR Prevention):** برای هر منبع حساس (کارنامه، سفارش، فاکتور، تلاش آزمون)، سرور مالکیت کاربر جاری را مستقیماً اعتبارسنجی می‌کند:
  ```typescript
  // نمونه کنترل در سرویس
  const attempt = await this.prisma.attempt.findUnique({ where: { id: attemptId } });
  if (attempt.userId !== currentUser.id && currentUser.role !== Role.Grandmaster) {
    throw new NotFoundException(); // ارسال 404 به‌جای 403 برای جلوگیری از شمارش شناسه‌ها
  }
  ```
- **حفاظت ۴۰۴ به جای ۴۰۳:** در صورت تلاش برای دسترسی به شناسه‌های غیرمجاز، به جای خطای ۴۰۳، خطای ۴۰۴ بازگردانده می‌شود تا نفوذگر نتواند از وجود داشتن یا نداشتن یک رکورد اطمینان یابد.

### ۱٫۳. اعتبارسنجی و بهداشت ورودی‌ها (V5)
- **اعتبارسنجی سفت‌وسخت با Zod و ValidationPipe:** تمام ورودی‌های کلاینت بر اساس اسکیمای صریح ارزیابی می‌شوند. پارامترهای اضافی (Payload Pollution) با فلگ `whitelist: true` خودکار دور ریخته می‌شوند.
- **مصونیت در برابر تزریق SQL (SQLi):** کلیه کوئری‌ها از طریق Prisma ORM و با متغیرهای پارامتری‌شده (Parameterized Queries) اجرا می‌شوند. هرگونه کوئری خام مستقیم بدون بررسی ممنوع است.
- **جلوگیری از XSS در محتوا:** متون ورودی در پاسخ‌نامه‌های تشریحی یا چت پشتیبانی، پیش از ذخیره با کتابخانه `DOMPurify` پالایش (Sanitize) می‌شوند.

### ۱٫۴. رمزنگاری در حرکت و سکون (V6 & V8)
- **ارتباطات تحت شبکه:** اجبار به پروتکل TLS 1.3 با سرتیفیکیت معتبر؛ هدر امنیتی HSTS با بازه دو ساله فعال است:
  ```
  Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
  ```
- **محرمانگی لاگ‌ها:** کدهای OTP، گذرواژه‌ها، توکن‌های JWT و اطلاعات کامل کارت‌های بانکی در هیچ لاگی (حتی در سطوح Debug) چاپ نمی‌شوند.

## ۲. سیاست‌های هدرهای امنیتی (HTTP Security Headers)

در لایه Nginx و فریم‌ورک Next.js هدرهای زیر روی تمام پاسخ‌ها تزریق می‌شوند:

| هدر امنیتی | مقدار پیکربندی | هدف امنیتی |
| :--- | :--- | :--- |
| **Content-Security-Policy (CSP)** | `default-src 'self'; script-src 'self' 'unsafe-inline'; img-src 'self' data: https:;` | مهار بارگذاری اسکریپت‌های ناشناس و XSS |
| **X-Frame-Options** | `DENY` | جلوگیری از حملات Clickjacking و جاسازی سایت در iframe |
| **X-Content-Type-Options** | `nosniff` | مهار حملات MIME-Sniffing |
| **Referrer-Policy** | `strict-origin-when-cross-origin` | جلوگیری از نشت شناسه‌ها و URLها در مراجعات خارجی |
| **Permissions-Policy** | `camera=(), microphone=(), geolocation=()` | مسدودسازی دسترسی‌های غیرضروری مرورگر |

## ۳. لایه‌بندی محدودیت نرخ (Rate Limiting & Anti-DDoS)

برای حفظ دسترس‌پذیری ۹۹٫۹۵٪ در پنجره‌های آزمون، محدودیت نرخ درخواست‌ها در دو لایه پیاده‌سازی می‌شود:

```
[ترافیک ورودی] 
      │
      ▼
[لایه ۱: Nginx Rate Limit] ─── (فیلتر حملات حجمی لایه ۷ و آی‌پی‌های مخرب)
      │
      ▼
[لایه ۲: NestJS Throttler + Redis] ─── (کنترل بیزینس لاجیک بر اساس کاربر/اکشن)
      │
      ├── اندپوینت لاگین: حداکثر ۵ درخواست در ۱۵ دقیقه
      ├── اندپوینت ثبت پاسخ آزمون: حداکثر ۱۰ درخواست در ۱۰ ثانیه
      └── سایر اندپوینت‌ها: حداکثر ۱۰۰ درخواست در دقیقه
```

### تنظیمات Throttler در NestJS:
```typescript
ThrottlerModule.forRootAsync({
  imports: [ConfigModule],
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    throttlers: [
      { name: 'default', ttl: 60000, limit: 100 },
      { name: 'auth', ttl: 900000, limit: 5 },
      { name: 'exam-heartbeat', ttl: 30000, limit: 3 }
    ],
    storage: new ThrottlerStorageRedisService(config.get('REDIS_URL'))
  }),
});
```
