> **نسخه:** ۱٫۰ — تدوین جامع بر مبنای PRD ۳٫۳، MVP ۲٫۳ و نمونه مرجع `session-lock`

> **وضعیت:** سند مشخصات فنی مصوب؛ مرجع پیاده‌سازی سرویس هویت و سشن در بک‌اند و فرانت‌اند.

## ۰. در یک نگاه و اصول حاکم

این سند جزئیات فنی، پروتکل‌های رمزنگاری، ساختار داده، سازوکار تبادل توکن‌ها و منطق مدیریت نشست‌های سامانه کندرلب را برای فاز A و با آمادگی کامل برای فاز B تعیین می‌کند.

### اصول معماری هویت:
1. **بدون فیلد نام کاربری (No Username):** شناسایی داخلی کاربران فقط با شناسه‌ی پایدار غیرقابل‌حدس (UUIDv4 سیستمی) انجام می‌شود.
2. **کوکی‌های امن HttpOnly (ضد نفوذ XSS):** توکن‌های ورود هرگز در `localStorage` کلاینت ذخیره نمی‌شوند و صرفاً در کوکی‌های رمزگذاری‌شده، `SameSite=Lax` و `Secure` تبادل می‌گردند.
3. **سقف دقیق ۲ نشست هم‌زمان (Max 2 Active Sessions):** هر حساب در هر لحظه حداکثر می‌تواند ۲ نشست فعال داشته باشد. مدیریت سشن‌ها به صورت اتمیک در Redis انجام می‌شود.
4. **تک‌دستگاهی بودن اتاق آزمون (Single Exam Device):** قفل ورود به سایت (سقف ۲ نشست) با قفل ورود به آزمون (دقیقاً ۱ دستگاه در لحظه با مکانیزم Heartbeat و Takeover) تفکیک شده است.
5. **آمادگی داده برای فاز B:** مدل هویتی از روز اول چندروشی (Multi-Provider) است تا افزودن ورود با شماره موبایل و کد یک‌بارمصرف (OTP) در فاز B بدون مهاجرت دیتابیس صورت گیرد.

## ۱. چرخه عمر توکن‌ها و نحوه ذخیره‌سازی

```
[کلاینت (Next.js / مرورگر)]
       │
       ├─── درخواست ورود (ایمیل/رمز یا گوگل) ───► [AuthService (NestJS)]
       │                                                │
       │                                                ├─ اعتبارسنجی هویت
       │                                                ├─ ثبت نشست در Redis (سقف ۲)
       │                                                └─ تولید جفت‌توکن
       │
       ◄─── Set-Cookie: condor_at (15min) ──────────────┘
       ◄─── Set-Cookie: condor_rt (30days) ─────────────┘
```

### ۱٫۱. مشخصات توکن‌ها

| توکن | نوع | طول عمر | نام کوکی | ذخیره‌سازی سمت سرور | کاربرد |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Access Token** | JWT امضاشده با RS256/HS256 | ۱۵ دقیقه | `condor_at` | بدون ذخیره (Stateless) | اعتبارسنجی درخواست‌های API و Routeها |
| **Refresh Token** | Opaque Token (رندوم ۶۴ بایتی) | ۳۰ روز | `condor_rt` | هش SHA-256 در PostgreSQL و Redis | تمدید Access Token بدون لاگین مجدد |

### ۱٫۲. تنظیمات کوکی‌ها (Cookie Security Directives)
```typescript
const COOKIE_OPTIONS = {
  httpOnly: true,
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'lax' as const,
  path: '/',
  domain: process.env.COOKIE_DOMAIN || undefined,
};
```

## ۲. مدیریت نشست‌ها و سقف ۲ دستگاه (Session Management)

### ۲٫۱. ساختار داده در Redis
برای مدیریت سریع، دقیق و با حداقل تأخیر نشست‌های فعال، از ساختارهای داده Redis زیر استفاده می‌شود:

1. **لیست نشست‌های کاربر:**
   - کلید: `user_sessions:{userId}` (از نوع Hash یا Sorted Set بر اساس زمان ایجاد)
   - ساختار: `{ [sessionId]: JSON.stringify(sessionMetadata) }`
2. **اطلاعات متادیتای هر نشست (`sessionMetadata`):**
   ```typescript
   interface SessionMetadata {
     sessionId: string;
     userId: string;
     deviceInfo: string;      // مثلاً "Chrome 122 on Windows"
     ipAddress: string;       // با ماسک‌گذاری جهت حفظ حریم خصوصی
     userAgent: string;
     createdAt: number;       // Unix timestamp
     lastActiveAt: number;
   }
   ```

### ۲٫۲. الگوریتم ثبت ورود و اخراج نشست مازاد (FIFO Kick-out)
طبق لاجیک پیاده‌سازی‌شده در `session-lock/src/session/session.service.ts`:
1. با لاگین موفق کاربر، شناسه سشن جدید (`sessionId`) تولید می‌شود.
2. تعداد سشن‌های فعال در کلید `user_sessions:{userId}` بررسی می‌شود.
3. **اگر تعداد سشن‌ها >= ۲ باشد:**
   - قدیمی‌ترین نشست (با کمترین `createdAt`) شناسایی می‌شود.
   - نشست قدیمی از Redis پاک شده و Refresh Token آن باطل می‌گردد.
   - دستگاه اخراج‌شده در اولین درخواست بعدی با خطای `401 AUTH_SESSION_REVOKED` مواجه و به صفحه لاگین هدایت می‌شود.
4. نشست جدید ثبت شده و تعداد سشن‌های فعال دقیقاً حداکثر ۲ می‌ماند.

## ۳. روش‌های احراز هویت (Authentication Providers)

```
┌────────────────────────────────────────────────────────┐
│            روش‌های هویت کاربری کندرلب                  │
├─────────────────────────┬──────────────────────────────┤
│ فاز A (فعال از روز اول) │ ۱. ایمیل + رمز عبور استاندارد│
│                         │ ۲. گوگل (Google OAuth 2.0)   │
├─────────────────────────┼──────────────────────────────┤
│ فاز B (آمادگی داده در A)│ ۳. شماره موبایل + OTP پیامکی │
└─────────────────────────┴──────────────────────────────┘
```

### ۳٫۱. ایمیل و رمز عبور (فاز A)
- **رمزنگاری پسورد:** الگوریتم `Argon2id` (پارامترهای: memoryCost: 65536, timeCost: 3, parallelism: 4) یا `bcrypt` با فاکتور کاری ۱۲.
- **تأیید ایمیل:** پس از ثبت‌نام، حساب در وضعیت `Pending_Verification` قرار می‌گیرد. یک توکن تصادفی ۳۲ بایتی با عمر ۲۴ ساعت تولید و لینک تأیید ایمیل می‌شود.
- **بازیابی رمز عبور:** ارسال لینک با توکن یک‌بارمصرف ۱ ساعته. پس از تغییر رمز، همه‌ی سشن‌های فعال کاربر لغو می‌شوند.

### ۳٫۲. ورود با گوگل (Google OAuth 2.0 - فاز A)
- کلاینت توکن `id_token` را از SDK گوگل دریافت و به اندپوینت `POST /auth/google` ارسال می‌کند.
- سرور امضای توکن را با کلیدهای عمومی گوگل اعتبارسنجی می‌کند:
  - بررسی `iss === 'https://accounts.google.com'`
  - بررسی `aud === process.env.GOOGLE_CLIENT_ID`
  - استخراج ایمیل و بررسی وضعیت `email_verified: true`
- اگر کاربری با این ایمیل وجود داشته باشد، سشن باز می‌شود. اگر نباشد، حساب جدید با وضعیت `Active` ایجاد می‌گردد.

### ۳٫۳. شماره موبایل و کد یک‌بارمصرف (OTP - فاز B)
- **آمادگی در فاز A:** جدول `Identity` دارای نوع `PHONE` و فیلد `phone_number` است.
- **مشخصات در فاز B:**
  - کد ۶ رقمی عددی با طول عمر ۲ دقیقه (۱۲۰ ثانیه).
  - ذخیره در ردیس با کلید `otp:{phoneNumber}`.
  - محدودیت سخت‌گیرانه: حداکثر ۵ ارسال در هر ساعت برای هر شماره.
  - ضدشمارش (Anti-Enumeration): پاسخ سرور به ارسال کد برای شماره‌ی موجود یا ناموجود کاملاً یکسان است.

## ۴. تکمیل پروفایل، اعتبارسنجی پایه‌ها و قوانین تسویه

طبق قواعد PRD و MVP، پروفایل دانش‌آموز در مرحله تسویه حساب تکمیل می‌شود:

```typescript
export const ProfileUpdateSchema = z.object({
  firstName: z.string().min(2, "نام باید حداقل ۲ حرف باشد").max(50),
  lastName: z.string().min(2, "نام خانوادگی باید حداقل ۲ حرف باشد").max(50),
  phoneNumber: z.string().regex(/^09[0-9]{9}$/, "شماره موبایل نامعتبر است"),
  grade: z.enum(["7", "8", "9", "10", "11"], {
    errorMap: (issue, ctx) => {
      return { message: "پایه تحصیلی باید یکی از پایه‌های هفتم تا یازدهم باشد" };
    }
  }),
  city: z.string().min(2, "نام شهر را وارد کنید"),
  school: z.string().min(2, "نام مدرسه را وارد کنید"),
});
```

> ⚠️ **قانون خط قرمز پایه دوازدهم:** اگر درخواستی حاوی `grade: "12"` به سرور ارسال شود، سرور خطای `422 INVALID_GRADE_12_NOT_ALLOWED` صادر می‌کند و ثبت پروفایل مسدود می‌شود.

## ۵. امنیت نقش مالک (Grandmaster Admin Hardening)

1. **تک‌حساب بودن:** فقط یک رکورد با نقش `Grandmaster` در دیتابیس وجود دارد (`is_owner = true`).
2. **الزام MFA:** ورود به پنل Grandmaster بدون تایید کد دومرحله‌ای (TOTP - Google Authenticator) غیرممکن است.
3. **مصونیت ساختاری (Hard-coded Immunity):**
   - هیچ اندپوینتی در API اجازه ویرایش نقش، تعلیق، محدودسازی یا حذف حساب Grandmaster را ندارد.
   - گارد دسترسی:
     ```typescript
     if (targetUser.role === Role.Grandmaster) {
       throw new ForbiddenException("حساب Grandmaster قابل تغییر توسط سایر نقش‌ها نیست");
     }
     ```
4. **انتقال مالکیت:** انتقال این نقش صرفاً توسط خود Grandmaster، با وارد کردن مجدد رمز عبور + کد MFA و تایید دو مرحله‌ای امکان‌پذیر است.

## ۶. کدهای خطا و پیام‌های فارسی ماژول Auth

| کد خطا | وضعیت HTTP | پیام فارسی کاربر | سناریوی رخداد |
| :--- | :---: | :--- | :--- |
| `AUTH_INVALID_CREDENTIALS` | 401 | ایمیل یا رمز عبور اشتباه است. | رمز نادرست یا ایمیل ناموجود (بدون افشای وجود حساب) |
| `AUTH_EMAIL_NOT_VERIFIED` | 403 | لطفاً ابتدا ایمیل خود را تأیید کنید. | تلاش برای خرید با حساب `Pending_Verification` |
| `AUTH_RATE_LIMITED` | 429 | تلاش بیش از حد؛ لطفاً ۱۵ دقیقه دیگر امتحان کنید. | بیش از ۵ تلاش ناموفق در ۱۵ دقیقه |
| `AUTH_SESSION_EXPIRED` | 401 | نشست شما منقضی شده است. لطفاً دوباره وارد شوید. | ابطال رفرش‌توکن یا انقضای ۳۰ روز |
| `AUTH_SESSION_REVOKED` | 401 | نشست شما به دلیل ورود از دستگاه جدید پایان یافت. | خروج توسط الگوریتم FIFO سقف ۲ دستگاه |
| `AUTH_ACCOUNT_SUSPENDED` | 403 | حساب کاربری شما به دلیل نقض قوانین معلق شده است. | وضعیت `Suspended` توسط مدیر |
| `AUTH_MFA_REQUIRED` | 403 | وارد کردن کد تأیید دومرحله‌ای الزامی است. | تلاش ورود ادمین بدون MFA |
| `INVALID_GRADE_12_NOT_ALLOWED`| 422 | امکان ثبت‌نام برای پایه دوازدهم وجود ندارد. | ارسال پایه ۱۲ در فرم پروفایل |
