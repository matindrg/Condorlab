## ۰. در یک نگاه و مدل تهدید (Threat Model)

در آزمون‌های آنلاین با ریسک بالا (High-Stakes) در المپیاد ایران، اعتبار کارنامه و رتبه‌بندی به **سلامت و عدالت رقابت** وابسته است. از آنجا که مراقب فیزیکی حضور ندارد، سامانه باید در برابر بردارهای حمله زیر مقاوم باشد:

```
┌────────────────────────────────────────────────────────┐
│               بردارهای حمله در آزمون آنلاین            │
├─────────────────────┬──────────────────────────────────┤
│ ۱. اشتراک حساب      │ ورود هم‌زمان دو نفر با یک اکانت  │
│ ۲. نشت سؤالات/PDF   │ دانلود یا اسکرپ خودکار محتوا     │
│ ۳. تقلب اینترنتی    │ باز کردن تب‌های گوگل/هوش مصنوعی  │
│ ۴. دستکاری کلاینت   │ ارسال بسته‌های ساختگی شبکه       │
│ ۵. حل سرعتی غیرعادی │ ثبت پاسخ‌ها در چند ثانیه         │
└─────────────────────┴──────────────────────────────────┘
```

## ۱. معماری قفل فعال دستگاه (Active Exam Device Lock)

هسته اصلی پلتفرم برای جلوگیری از آزمون هم‌زمان، سامانه قفل تک‌دستگاهی پیاده‌سازی‌شده در `session-lock` با ترکیب **Redis 7 + اسکریپت‌های اتمیک Lua** است:

```
[دستگاه A (فعال)]                   [سرور و Redis]                   [دستگاه B (مهاجم)]
       │                                  │                                  │
       ├─── POST /exam/start ────────────►│ lock: owner=A, ver=1             │
       │◄── 200 OK (قفل اختصاص یافت) ─────┤                                  │
       │                                  │◄─── POST /exam/start ────────────┤
       │                                  ├─── 409 EXAM_LOCKED ─────────────►│
       │                                  │    (نمایش مدال Takeover)         │
       │─── Heartbeat هر ۳۰ ثانیه ───────►│ تمدید TTL (180s)                 │
       │                                  │                                  │
       │                                  │◄─── POST /exam/takeover ─────────┤
       │                                  │ lock: owner=B, ver=2, count=1    │
       │                                  ├─── 200 OK (قفل تسخیر شد) ────────►│
       │                                  │                                  │
       │─── Heartbeat بعدی ──────────────►│ بررسی مالکیت: مالک B است!       │
       │◄── 403 EXAM_LOCK_LOST ───────────┤                                  │
       │ (هدایت اجباری به داشبورد)        │                                  │
```

### ۱٫۱. ساختار داده قفل در Redis
- **کلید اصلی قفل:** `exam_lock:{attemptId}` (از نوع Hash)
  - `ownerDeviceId`: شناسه یکتای دستگاه فعال (تولیدشده در کلاینت و ذخیره در سشن)
  - `version`: شمارنده افزایشی نسخه قفل
  - `lastHeartbeat`: زمان آخرین ضربان قلب
  - `TTL`: ۱۸۰ ثانیه (۳ دقیقه)
- **کلید شمارنده تسخیر (Takeover Count):** `exam_takeover_count:{attemptId}`
  - نوع: عددی (Integer)
  - **سقف مجاز:** حداکثر ۲ بار تسخیر در طول آزمون. تلاش سوم با خطای `403 TAKEOVER_LIMIT_REACHED` مسدود می‌شود و دانش‌آموز باید به پشتیبانی ارجاع داده شود.

### ۱٫۲. اتمیک بودن تغییرات با اسکریپت Lua (Lua Script Execution)
برای جلوگیری از هرگونه Race Condition، تمام عملیات قفل، تمدید و تسخیر در یک Round-Trip با اسکریپت Lua در ردیس اجرا می‌شوند:

```lua
-- نمونه لاجیک تمدید و اعتبارسنجی قفل (Heartbeat Script)
local lockKey = KEYS[1]
local deviceId = ARGV[1]
local now = ARGV[2]
local ttl = tonumber(ARGV[3])

local currentOwner = redis.call('HGET', lockKey, 'ownerDeviceId')

if not currentOwner then
    return redis.error_reply("EXAM_LOCK_MISSING")
end

if currentOwner ~= deviceId then
    return redis.error_reply("EXAM_LOCK_LOST")
end

redis.call('HSET', lockKey, 'lastHeartbeat', now)
redis.call('EXPIRE', lockKey, ttl)
return 1
```

> ⚠️ **قانون کلیدی:** دستگاهی که قفل را از دست داده (`EXAM_LOCK_LOST`) تحت هیچ شرایطی اجازه نوشتن پاسخ جدید روی سرور را ندارد؛ حتی اگر پاسخ‌ها در صف آفلاین دستگاه A مانده باشند، سرور آنها را رد می‌کند.

## ۲. پایداری و یکپارچگی ثبت آفلاین پاسخ‌ها (Offline Queue Integrity)

در شرایط نوسان اینترنت ایران، سامانه باید قطعی موقت را بدون از دست دادن پاسخ‌ها و بدون باز کردن راه تقلب مدیریت کند:

1. **صف محلی در کلاینت (`localStorage`):**
   - با تغییر پاسخ هر سؤال، اگر ارتباط قطع باشد، پاسخ در صف کلاینت همراه با شناسه سؤال، مقدار پاسخ، و شماره توالی زمان (`client_timestamp`) ذخیره می‌شود.
   - سقف حجم صف: حداکثر برابر با تعداد کل سؤالات آزمون (پیش‌فرض ۳۰۰ آیتم) و سقف ۱ مگابایت برای جلوگیری از حملات Memory Overflow.
2. **ارسال دسته‌ای با بازگشت اینترنت:**
   - با اولین Heartbeat موفق بعدی، تمام صف آفلاین به همراه آخرین وضعیت ارسال می‌شود.
   - سرور بررسی می‌کند که زمان ثبت پاسخ‌ها از زمان پایان رسمی آزمون نگذشته باشد.
3. **مهلت خروج از صف پس از پایان زمان آزمون (Grace Period):**
   - به دانش‌آموز پس از صفر شدن زمان آزمون، حداکثر **۳۰ ثانیه** فرصت داده می‌شود تا پاسخ‌هایی که در صف آفلاین مانده‌اند به سرور تخلیه شوند. این پاسخ‌ها در دیتابیس با برچسب `accepted_after_deadline` ذخیره می‌شوند تا در بررسی‌های داوری قابل تفکیک باشند.

## ۳. ردگیری رفتاری و تله‌متری فرانت‌اند (Forensic Telemetry)

برای تشخیص تقلب‌های چندپنجره‌ای و جستجو در اینترنت حین آزمون، رخدادهای زیر به صورت نامحسوس ثبت و در لاگ آزمون ذخیره می‌شوند:

### ۳٫۱. رویدادهای تحت پایش
1. **خروج از تب آزمون (`visibilitychange`):**
   - با رویداد `document.visibilityState === 'hidden'`، زمان دقیق خروج کاربر و مدت‌زمان دوری از تب تا میلی‌ثانیه ثبت می‌شود.
2. **عدم تمرکز روی پنجره (`window.onblur`):**
   - ثبت خروج ماوس یا فوکوس روی سایر برنامه‌ها (مانند تلگرام، ورد یا مرورگر ثانویه).
3. **تلاش برای کپی یا پرینت:**
   - مسدودسازی کلیدهای ترکیبی `Ctrl+C`، `Ctrl+P`، `Ctrl+U` (مشاهده سورس) و کلیک راست (`contextmenu`) در صفحه آزمون.
4. **تغییر ابعاد غیرعادی پنجره:**
   - نشان‌دهنده استفاده هم‌زمان از Split-Screen برای تقلب در کنار آزمون.

### ۳٫۲. ساختار لاگ رویدادهای تله‌متری (`telemetry_events`)
```json
{
  "attemptId": "att_7f3k2m9q",
  "eventType": "TAB_BLUR",
  "startedAt": 1729851200500,
  "durationMs": 4200,
  "details": { "target": "external_window" }
}
```

> **اثر رویدادها در فاز A:** این رویدادها در فاز اول صرفاً «ثبت و پایش» می‌شوند و باعث قطع ناگهانی آزمون دانش‌آموز نمی‌شوند (تا خطاهای ناخواسته باعث استرس نشود)؛ اما در پنل مدیریت، یک «شاخص سلامت آزمون (Integrity Score)» برای هر کارنامه محاسبه می‌شود.

## ۴. جلوگیری از نشت سؤالات و سرقت PDF (Scraping & Leak Prevention)

1. **واترمارک داینامیک نامحسوس (Dynamic Forensic Watermark):**
   - روی تمام صفحات PDF و در پس‌زمینه نمای سؤالات وب، اطلاعات کاربر (نام، شماره تماس، شناسه تلاش و IP) به صورت مورب، نیمه‌شفاف و تکرارشونده رندر می‌شود.
   - اگر عکسی از صفحه گرفته شده و در گروه‌های تلگرامی منتشر شود، هویت داوطلب فوراً شناسایی می‌گردد.
2. **رندرینگ محافظت‌شده در PDF.js:**
   - فایل خام PDF هرگز با لینک مستقیم در اختیار مرورگر قرار نمی‌گیرد.
   - فایل در قالب Stream امضاشده با توکن ۱ دقیقه‌ای بارگذاری شده و مستقیماً روی بوم HTML5 Canvas نقاشی می‌شود.
3. **تغییر اسامی کلاس‌های CSS (CSS Obfuscation):**
   - گزینه‌ها و متن سوالات در فرانت‌اند با کلاس‌های درهم‌ریخته کامپایل می‌شوند تا ربات‌های اسکرپر با سلکتورهای ساده قادر به استخراج تست‌ها نباشند.

## ۵. عدم افشای کلید در سمت کلاینت (Zero Knowledge Client)

- در طول برگزاری آزمون، بسته داده‌ای که به مرورگر فرستاده می‌شود **فقط و فقط شامل صورت سؤال، گزینه‌ها و رسانه است**.
- هیچ داده‌ای در مورد اینکه کدام گزینه کلید درست است، چه در آبجکت‌های جاوااسکریپت، چه در فراداده‌های پنهان یا کدهای HTML وجود ندارد.
- تصحیح اوراق به صورت ۱۰۰٪ در سمت سرور و پس از پایان بازه آزمون توسط سرویس ارزیابی (`GradingService`) انجام می‌شود.
